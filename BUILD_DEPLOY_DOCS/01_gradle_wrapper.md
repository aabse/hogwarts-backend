# Gradle Wrapper

Files covered:

- [`gradlew`](../gradlew)
- [`gradlew.bat`](../gradlew.bat)
- [`gradle/wrapper/gradle-wrapper.jar`](../gradle/wrapper/gradle-wrapper.jar)
- [`gradle/wrapper/gradle-wrapper.properties`](../gradle/wrapper/gradle-wrapper.properties)

The four files form a single mechanism — the **Gradle Wrapper** — so they are documented together.

## What problem it solves

The Wrapper lets you build the project without Gradle installed globally on the machine, and guarantees that **everyone** (developers, CI, Docker) uses exactly the same Gradle version. It is the first link in any build flow of this repo: every command (`./gradlew check`, `./gradlew :wizard-service:bootJar`, etc.) goes through here before reaching `settings.gradle` or the `build.gradle` files.

## `gradle-wrapper.properties`

```properties
distributionBase=GRADLE_USER_HOME
distributionPath=wrapper/dists
distributionUrl=https\://services.gradle.org/distributions/gradle-9.2.1-bin.zip
networkTimeout=10000
validateDistributionUrl=true
zipStoreBase=GRADLE_USER_HOME
zipStorePath=wrapper/dists
```

- **Pinned version: Gradle 9.2.1**, `-bin` distribution (binaries only, no sources/documentation — a lighter download than `-all`).
- `distributionBase` / `zipStoreBase = GRADLE_USER_HOME`: the downloaded distribution is cached in `~/.gradle/wrapper/dists`, **not** inside the repo. That is why a new machine takes a bit longer the first time it runs `./gradlew` (it downloads ~100 MB), but later builds reuse the cache.
- `networkTimeout=10000`: 10-second network timeout when downloading the distribution.
- `validateDistributionUrl=true`: validates the integrity/authenticity of the downloaded distribution (security hardening in recent wrapper versions).

This file is the **single** source of truth about which Gradle version the project uses. To change the version, edit only this file (or run `./gradlew wrapper --gradle-version=X`).

## `gradlew` / `gradlew.bat`

They are the launcher scripts generated by Gradle (not edited by hand). `gradlew` is the macOS/Linux version (shell script) and `gradlew.bat` the Windows version (batch). Both do the same thing:

1. Resolve `APP_HOME` (the project root), following symlinks if needed.
2. Locate a valid JDK (`JAVA_HOME` or `java` on the `PATH`); if they find none, they fail with an explanatory message.
3. Start a lightweight JVM (`-Xmx64m -Xms64m`) whose only job is to run `gradle-wrapper.jar`.
4. Delegate the actual build to that JVM: `java -jar gradle/wrapper/gradle-wrapper.jar <arguments>`.

## `gradle-wrapper.jar`

It is the binary (~46 KB) that both scripts invoke. Its logic: read `gradle-wrapper.properties`, download (if not cached) the Gradle 9.2.1 distribution given in `distributionUrl`, validate it and finally hand control to that Gradle installation to run the requested task (`check`, `bootJar`, `bootRun`, etc.).

It is a binary and, by Gradle convention, it **must** be committed to the repository so the wrapper works on a fresh clone without manual steps. That is why the root `.gitignore` explicitly excludes it from the rules that ignore build artifacts:

```gitignore
.gradle
build/
!gradle/wrapper/gradle-wrapper.jar
```

## Role in the build/deploy pipeline

- **Local**: every build command (`./gradlew check`, `./gradlew testAll`, `./gradlew :wizard-service:bootRun ...`) goes through here first.
- **Dockerfile**: the build stage of [`wizard-service/Dockerfile`](07_wizard_service.md) copies `gradlew`, `gradlew.bat` and the `gradle/` folder into the container and runs `./gradlew :wizard-service:bootJar` inside the image — the wrapper is what makes it possible to build without a base image with Gradle preinstalled.
- **Buildpacks**: Cloud Native Buildpacks for Java/Gradle also detects and uses `gradlew` automatically inside the module directory (see [`README.md`](README.md)).
