# `hogwarts.iml`

File covered: [`hogwarts.iml`](../hogwarts.iml)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<module type="JAVA_MODULE" version="4">
  <component name="NewModuleRootManager" inherit-compiler-output="true">
    <exclude-output />
    <content url="file://$MODULE_DIR$" />
    <orderEntry type="sourceFolder" forTests="false" />
  </component>
</module>
```

## What it is

An `.iml` file is metadata specific to **IntelliJ IDEA** (and derivatives such as Android Studio): it describes an IDE "module" — its root folder, whether the compiler output is inherited from the project, which folders to exclude from indexing, etc. This `hogwarts.iml` corresponds to the project's root module and is auto-generated by IntelliJ when importing/opening the `hogwarts-backend` folder.

Breakdown of its content:
- `type="JAVA_MODULE"`: tells the IDE to treat this folder as a Java module.
- `inherit-compiler-output="true"`: the compiler output directory (inside the IDE) is inherited from the global project configuration, instead of being defined per module.
- `<exclude-output />`: excludes the output folder (equivalent to `build/`) from the IDE's indexing.
- `<content url="file://$MODULE_DIR$" />`: the module's content is the folder where the `.iml` itself lives.
- `<orderEntry type="sourceFolder" forTests="false" />`: standard classpath entry for the source folders.

## What it is NOT

**It takes no part at all in the real build.** Gradle does not read `.iml` files; Docker does not copy it; Cloud Build/Buildpacks ignore it. It is purely editor configuration. If it is deleted, IntelliJ simply regenerates it the next time the project is opened or synced (usually from the information in `settings.gradle` and the `build.gradle` files).

## Note about `.gitignore`

The root `.gitignore` includes a standard IntelliJ section that ignores `*.iml`:

```gitignore
### IntelliJ IDEA ###
.idea
*.iws
*.iml
*.ipr
```

In other words, the intent declared in `.gitignore` is that `.iml` files are **not** versioned (they are local IDE artifacts, prone to differing between machines). The presence of `hogwarts.iml` in the working tree does not contradict this in a problematic way — it is simply a file generated locally by IntelliJ that coexists with the rest of the code; there is no need, and it is not advisable, to treat it as part of the build/deploy process documented here.

## Role in the build/deploy pipeline

None. It is documented for completeness (it was explicitly listed as a file to describe), but it plays no part in local compilation, in `./gradlew check`, in building images (Dockerfile or Buildpacks), or in the deployment to GKE.
