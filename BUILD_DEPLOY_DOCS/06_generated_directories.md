# Generated directories: `/build` and `/.gradle`

Folders covered:

- [`/build`](../build)
- [`/.gradle`](../.gradle)

They are documented together because both are **state generated** by the Gradle build process (not source code), both are excluded from git, and both are recreated automatically on every build — they must never be edited or committed by hand.

## `/build` (root)

It is the build output of the **root project** (each subproject has its own internal `build/`, e.g. `wizard-service/build/`). Typical content:

```
build/
├── classes/         # compiled .class files
├── generated/        # sources/resources generated by plugins
├── reports/          # jacoco, checkstyle, test reports, etc.
│   └── jacoco/jacocoRootReport/{jacocoRootReport.xml,html/}
├── resources/         # processed resources
├── test-results/       # test results (XML, used by CI for reporting)
└── tmp/             # temporary files of Gradle tasks
```

This is where, among other things, the outputs of the custom tasks defined in [`build.gradle`](02_root_build_gradle.md) land: `jacocoRootReport` explicitly writes to `build/reports/jacoco/jacocoRootReport/`. In each subproject, `build/libs/*.jar` is the artifact produced by `bootJar` and consumed by the `wizard-service` `Dockerfile` (`COPY --from=build /workspace/wizard-service/build/libs/*.jar app.jar`, see [`07_wizard_service.md`](07_wizard_service.md)).

## `/.gradle` (root)

It is the **project's local cache** (different from `~/.gradle`, the global `GRADLE_USER_HOME` mentioned in [`01_gradle_wrapper.md`](01_gradle_wrapper.md)). Typical content:

```
.gradle/
├── <version>/          # Gradle's internal metadata/cache for that version (e.g. 9.2.1)
├── buildOutputCleanup/  # state of Gradle's output cleanup service
├── file-system.probe    # detection of the filesystem's case sensitivity/timestamp granularity
└── vcs-1/               # VCS mapping cache (for included builds/source dependencies)
```

It enables faster incremental builds (Gradle avoids recompiling/re-testing what did not change), but it is purely a local machine artifact — it must not be shared between environments or copied into a container image.

## Why they are (correctly) outside git

Root `.gitignore`:

```gitignore
.gradle
build/
!gradle/wrapper/gradle-wrapper.jar
!**/src/main/**/build/
!**/src/test/**/build/
```

- `.gradle` and `build/` are ignored at any level of the tree (this affects both the root and `wizard-service/build/`, `inventory-service/build/`, `duel-service/build/`).
- The two exceptions (`!**/src/main/**/build/`, `!**/src/test/**/build/`) are an unusual defensive safeguard: they protect any file that happens to live inside a folder literally named `build` within a source tree (`src/main/.../build/...`), distinguishing it from the build output directory at the root of each module.
- The `gradle-wrapper.jar` exception (see [`01_gradle_wrapper.md`](01_gradle_wrapper.md)) is needed because that binary must be committed.

## Role in the build/deploy pipeline

These directories are **transient and reproducible**: any environment (a laptop, a CI runner, the build stage of a `Dockerfile`, or Cloud Build running Buildpacks) regenerates them from scratch from the source code and `build.gradle`/`settings.gradle`. That is why the `wizard-service` `Dockerfile` never copies `build/` or `.gradle/` into the container — it copies the source code and runs `./gradlew ... bootJar` inside the image, letting Gradle regenerate `build/libs/*.jar` in that isolated environment.
